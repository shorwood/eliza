# PR 001 — Release compiler optimizations

Full LTO with one codegen unit is retained. Replay improves in all three pairs,
with a 10.0% median paired reduction, and no generation case regresses.

## Change and build comparison

The candidate adds `lto = true` and `codegen-units = 1` to the workspace release
profile, matching those two settings in [Hurl](https://github.com/Orange-OpenSource/hurl/blob/master/Cargo.toml).
Panic handling remains unchanged. Cargo's bench profile inherits these
release settings. See the [Cargo profile reference](https://doc.rust-lang.org/cargo/reference/profiles.html).

Baseline source is commit `acb29dd`, with Cargo release defaults. The candidate
implementation is commit `c19a6cb` and changes only the root release profile.
Both saved server and benchmark binaries
use the same fixtures, lockfile, pinned Rust `1.97.0-nightly` (`e8e4541ff`), and
LLVM 22.1.2. Builds use separate fresh target directories, one build job, and
disabled incremental compilation. No other build runs during either build.

| Build observation | Baseline | Full LTO, one codegen unit |
| --- | ---: | ---: |
| Clean server release build | 147 s | 134 s |
| Subsequent benchmark build | 87 s | 100 s |
| Server executable size, before stripping | 19,717,480 B | 14,650,440 B |

The benchmark build reuses dependencies from its variant's preceding server
build; it is not another independent clean build. Each build time is one wall
clock observation. The candidate executable is 25.7% smaller. Neither size nor
these individual build times establishes a runtime speedup. Full LTO did not
exceed the preselected build-cost threshold of twice baseline, so Thin LTO was
not required by that rule.

Saved manifests, binaries, hashes, compiler/environment details, build logs,
acceptance rule, and run order are under `target/benchmarks/pr001/`.

## Runtime method

Six existing Criterion cases cover session startup, 100-turn ELIZA replay,
100-turn ASCII/Unicode completions, and short/medium Flite synthesis at 24 kHz.
Both variants run on logical CPU 16. Criterion uses 50 samples, three-second
warmup, and ten-second measurement. Three independent pairs alternate order:
baseline/candidate, candidate/baseline, then baseline/candidate. These are elapsed
times, separate from the HTTP process CPU counters.

HTTP compares `chat-short`, `chat-long`, and `speech-medium-pcm`, each at closed
concurrency eight and open ten requests/second. Each point starts a fresh server,
warms for five seconds, and measures for thirty seconds. The same saved load
generator is used for every variant. Server CPUs 16–17 and client CPUs 18–21 are
separate E cores, with two Tokio server workers. There are three alternating
paired rounds. Compilation and tests finish before timing starts. These focused
windows do not establish the full suite's sixty-second capacity baseline.

The saved load client predates the release-profile change and its metadata
contains a hard-coded `Cargo defaults` label. For this comparison, the actual
profile is established by each variant's saved `Cargo.toml`, executable hash,
and build log. The working-tree diff captured by the client is not the source
provenance of the saved baseline executable.

The preselected acceptance rule requires improvement in all three paired replay
runs or a representative HTTP CPU/request case, with at least 5% median
improvement. Reject a greater-than-5% regression in all three pairs of another
representative generation case. Inspect HTTP latency, failures, and dropped
arrivals separately; keep unlike workloads and repetitions separate.

Times are the median of three independent Criterion mean estimates, in
microseconds. Reduction ranges use each pair's means, not confidence intervals.
Cases and samples are not pooled. All six cases improve in every pair.

## HTTP results

CPU/request includes all server threads, user and kernel time, and the final
drain. All 36 paired HTTP points completed without failures or dropped arrivals.
CPU and p95 columns are medians of three independent per-point summaries;
reduction ranges compare each pair's CPU/request. Percentiles are not pooled.

| Workload / load | Baseline CPU µs/request | Full LTO CPU µs/request | Paired CPU reduction | Baseline p95 ms | Full LTO p95 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| Short chat / concurrency 8 | 869.2 | 804.0 | 7.3–7.6% | 5.275 | 4.887 |
| Long chat / concurrency 8 | 1,478.8 | 1,337.8 | 9.4–9.7% | 8.999 | 8.139 |
| Medium PCM speech / concurrency 8 | 11,467.0 | 10,975.0 | 4.0–4.4% | 73.023 | 71.871 |
| Short chat / 10 requests/s | 1,100.0 | 1,066.7 | 0.0–8.8% | 3.005 | 3.079 |
| Long chat / 10 requests/s | 1,700.0 | 1,533.3 | 6.0–11.8% | 3.259 | 2.985 |
| Medium PCM speech / 10 requests/s | 11,866.7 | 11,333.3 | 4.2–5.3% | 53.503 | 52.735 |

Median closed-model successful throughput rises from 2,274 to 2,460 requests/s
for short chat, 1,342 to 1,484 for long chat, and 134.2 to 138.5 for speech.
The open-model points all sustain their offered ten requests/s. Low-rate short
chat has mixed paired latency results and coarser CPU/request precision: a
10-ms process CPU tick corresponds to approximately 33 µs/request over its
300 successes. Its median p95 is slightly slower despite two improved pairs.
There is no consistent latency regression across all three pairs.

`target/benchmarks/pr001/summary.json` retains per-pair means, generation
confidence intervals, CPU/request, throughput, latency, and error counts.
Each HTTP directory retains complete request samples, histograms, and process
snapshots. These results satisfy the preselected rule and support retaining
the profile locally. Stable-hardware verification and a full capacity sweep
remain necessary for broader throughput claims.

## Host failures

The initial baseline HTTP warmup on P-core CPUs 0 and 2 terminated with SIGSEGV.
A separate short diagnostic on those P cores terminated with SIGABRT and
`double free or corruption (out)`. Both failures precede any candidate HTTP
measurement and use the default-profile baseline binary. The same baseline
binary passed a short concurrency-eight/open-rate-ten diagnostic on E cores.

Failed request samples, server logs, core information, and GDB output are retained.
The failed initial attempt is not pooled with the paired measurements. The
E-core assignments were selected for both variants before restarting the pairs.
CPU correlation does not establish the failure's cause; software and compiler
defects remain possible. This host has reported i9-14900K instability, and the
earlier [baseline](BASELINE.md) records a similar unresolved failure. All local
performance results remain provisional.

## Validation

`CARGO_INCREMENTAL=0 CARGO_BUILD_JOBS=1 just ok` passed, including workspace and
HTTP tests, Clippy, and Dylint. `nix build .#eliza --no-link --cores 1 --max-jobs 1`
passed, including release CLI/HTTP tests, installation, and prohibited toolchain
reference checks. Its complete package log is retained with the build artifacts.
`just ok` also passed after the audit fix in `6cdb2f7`, which replaces the
hard-coded profile label with the workspace manifest in future benchmark runs.

After the model-alias implementation and audit, the final release smoke check
passed all 76 generation cases and 46 HTTP load points with no failures or
dropped arrivals. It ran `just bench-smoke` inside the pinned environment with
`taskset -c 16-31`, keeping both server and client on disjoint E-core sets.
Smoke timings validate fixtures and execution, rather than capacity.
